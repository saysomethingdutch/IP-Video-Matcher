1. **原表的录像名写错，台账就关联不上。**
   - 2591 号的 522–548 共 27 行，原表写的是 MAH00737，实际在 MAH00738（原表没引用这个文件）。

   - 台账把原表的录像名当成硬约束，于是这 27 行都成了"无会话"，画面也跟着跳过。
2. **分P共用一个 BV，台账分不开。**
   - 4086 号每个 BV 有 3–4 个分P，标题分别以"七时16-1""七时16-2"……结尾。
   - 结果：6 行无会话，13 个会话没关联上。
3. **缺少声音信息。**
   - 4086 号"丁禹兮考古向"系列是**不出镜、只用声音点评**的 reaction。没有语音转写，机器看到的只有原剧画面和台词，就把其中 7 行判成了原片搬运。人工听得到点评，判的是"跳播+reaction"。
   - 2591 号有 10 行是"原剧画面 + UP 主字幕讲剧情"。人工意见里都写了"配以较为浪漫的 bgm"，判为混剪类；机器听不到配乐，判成了剧情解说。

## 1. 台账关联（改 `pilot/ledger`）

1. **关联不再依赖原表的录像名。**
   - 在本批全部录像里，按 BV 和标题做闭集关联。候选限于本批的行。
   - 原表录像名与实际不一致的行，标黄"原表录像名为 X，实际在 Y"。这一点可能对被告有利，要保留。
2. **分P按"分P标识"关联。**
   - 画面顶部的分P标题（如"七时25-4"）、播放器的"N/M"读数、标题尾部的"-N""（N）""P N"，都能用来区分分P。
   - 同一个 BV 下，按分P标识一一对应。分不开的，标黄并列出候选。
3. **回归测试**：
   - 4086 号：44 行中，有会话的应 ≥ 42 行；未关联的会话应 ≤ 3 个。
   - 2591 号：522–548 应能关联上 ≥ 25 行。
   - 试点 169 行的现有结果不能变差。

## 2. 声音这一路（新模块 `pilot/audio`，只在本机跑）

1. **引擎**：FunASR 的 SenseVoice-Small，本地运行，不上传音频（D-019）。它能同时给出中文转写和声音事件（BGM、说话、笑声等）。泰语行继续沿用已有的 whisper 结果。
2. **范围**：只处理台账里"已播放"的片段。
3. **每行输出**：
   - 转写文本和时间戳；
   - 与原剧台词索引对照：能对上的是原剧台词，对不上的算"UP 主口播"；
   - 说话占比、BGM 占比、笑声等事件，以及"疑似 UP 主配乐"。原剧台词很少、BGM 占主导，就判为疑似 UP 主配乐。
4. **速度**：在一条 30 分钟以上的录像上测实时倍数，写进交付说明，给逐玉估时间用。
5. **接口**：输出放在 `<case>/audio/<row>.json`。Claude Code 的分类会读取（WO-004b-R2）。
